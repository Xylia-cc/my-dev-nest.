# 2026-10-06 工作日志

## 修复：替换组容量计算错误（库存相加再折算 → 应分别折算再相加）

### 问题现象
用户用模板 `组装量计算模板261006-新品.xlsx` 测试，反馈：
`a-vps-ky 1822750` 父件下的子件 `1821566`，库存不足一套，覆盖套数为 0，却出现在消耗明细中。

### 数据现场
1822750 的替换组 `G:1771111`（消耗顺序：替代件先扣，耗尽后用主件）：
- 替代件 **1821566**：库存 **3**，配比 2
- 主件 **1771111**：库存 **1**，配比 2

### 根因分析
引擎 Phase 1 计算 slot 容量时：
```js
eff += qty / c.ratio;            // 每个子件分别除，累加小数
var cap = Math.floor(eff + 1e-9); // 最后统一 floor
```
- 引擎算法：`(3/2) + (1/2) = 2.0` → cap = **2 套**（错误）
- 正确算法（规则②「自身库存÷自身配比折算套数相加」）：`floor(3/2) + floor(1/2) = 1 + 0 = ` **1 套**

**核心问题**：把不同料的库存**相加后再折算**，等价于允许"替代件碎片 + 主件碎片"拼成一套——但物理上它们不能互相凑数（各占 1 个、配比均为 2，谁都不够）。

后果链：
1. 容量被高估为 2 套 → `k = 2`
2. `rel1Sets = 1`（替代件能组 1 套），`sets2 = 2 − 1 = 1`
3. 关系2 环节 `consumeAlts(1)`：替代件剩 1 个，`take = min(1, 2) = 1`，`coverSets = floor(1/2) = 0`
4. 输出明细行「覆盖=0套、消耗=1」← 用户看到的问题行

### 修复内容
三处统一改为「各子件分别 floor 折算后相加」：
1. **Phase 1** slot 容量：替换组（`slot.children.length > 1 || /^G:/`）走 `Math.floor(qty / c.ratio)` 累加；普通 slot 保持原逻辑
2. **Phase 3** 替换组 maxSets：`Σ floor(avail_i / ratio_i)`（共享子件取 allocated，非共享取 pool）
3. **Phase 3.5 步骤 3** 同样改为分别折算

### 修复后结果
- `1822750 a-vps-ky`：组装量 **2 → 1**（正确）
- 消耗明细中「覆盖0套却有消耗」的脏行**全部消失**
- 全库校验：862 个子件，**0 超扣，0 个覆盖0却有消耗的行**
