## 修复：替代件碎片被消耗但不计套数（consumeAlts 未取整到配比倍数）

### 用户诉求
模板 `E:/1新建文件夹/桌面/组装量计算模板.xlsx`，`a-eu-jc 1779470` 下子件 `1779594`：
> 库存只有一个，不满足一套，覆盖套数为 0，**此时不使用替代件，且不展示出来此条消耗明细**

### 数据现场
替换组 `G:1812522`（替代件 `1779594`，主件 `1812522`），需求 54，组装 54（齐套满足）：
- 关系1 = 42 套：替代件 1779594 用掉 84 个
- 关系2 = 12 套：替代件剩 1 个碎片（不够一套），应由主件 1812522 补足

修复前消耗明细出现脏行：`1779594 覆盖=0 消耗=1 关系=2`

### 根因分析
Phase 4 替换组处理的 `consumeAlts` 只判断 `take > 0`，**没有把 take 取整到配比倍数**：
```js
var take = Math.min(info.avail, needQty);   // avail=1, needQty=24 → take=1
if (take > 0) {
  var coverSets = Math.floor(take / info.ratio);  // floor(1/2)=0
  used.push({ used: take, setsCovered: coverSets });  // ← 输出「覆盖0、消耗1」
  ...
}
```
不足一套的碎片被消耗、被扣库存、被展示，但计 0 套。

> 注：这与 10-06 修复的「替换组容量库存相加再折算」是**两个独立问题**。10-06 那次是容量被高估导致 k 虚高；本次是正常场景下替代件用剩的碎片被误消耗。

### 修复内容
`consumeAlts` 中把 take 向下取整到配比倍数，只取能凑成完整套数的量：
```js
var take = Math.min(info.avail, needQty);
take = Math.floor(take / info.ratio) * info.ratio;  // ★ 碎片不使用、不展示、不扣库存
if (take > 0) { ... }
```

### 修复后结果
- `1779470 a-eu-jc`：组装量仍 **54**（齐套满足，不受影响）
- 关系2 中 `1779594` 的脏行（覆盖0/消耗1）**消失**
- 关系2 的 12 套改由主件 `1812522` 承担（覆盖12/消耗24）✅

## 方案 + 实施：slot 容量表新增「剩余库存」列（I 列，口径A 已确认并实施）

### 需求（用户提出，暂不实施）
在「各父件 slot 容量」表新增一列「剩余库存」，= 对应(仓库+SKU)的库存 − 消耗库存。

### 现状调研（列结构）
当前 8 列，页面表格与 CSV/XLSX **列序不一致**（已知历史问题）：
- 页面表格：仓库 | 父件 | slot | 子件(主/替代) | 配比 | 库存 | 转化系数 | slot容量
- CSV/XLSX：仓库 | 父件 | slot | slot容量 | 配比 | 子件 | 库存 | 转化系数

行粒度 = (仓库, 父件, slot, 子件)；替换组内替代件/主件各占一行。
新增列 → 第 9 列（I 列）。

### 数据来源（已确认可用）
- `res.consumption[]`：`{warehouse, child, used, remaining}`，key = `仓库||子件`
  - `remaining` = pool 扣减后的剩余（engine.js:959-963 已算好）
- `ch.inv`：Phase 1 快照的初始库存
- 计算：`remainMap[仓库||子件] ?? ch.inv`（未被消耗的子件 → 剩余 = 初始库存）

### 两种口径（待用户确认）
- **口径 A（全局剩余）**：该 SKU 在该仓被**所有父件**消耗后的剩余 → 同一(仓库,SKU)在多行显示相同值
- **口径 B（本父件剩余）**：仅减去**本行父件**对该子件的消耗 → 每行值可能不同
- 用户原话"每条对应仓库+sku 库存减去消耗库存" → 倾向 **口径 A**

### 实施点（改 index.html 4 处 + gen_test_report.js 可选）
1. `index.html:367` 页面表头（加 `<th>剩余库存</th>`）
2. `index.html:371-375` 页面表格行
3. `index.html:410 / 414-423` CSV 表头与行
4. `index.html:449 / 453-462` XLSX 表头与行
5. `gen_test_report.js:39-44`（可选）—— 当前为简化版（子件合并成字符串、无库存列），需展开到子件级才能显示单 SKU 剩余

### 验证方式
- 抽查：某(仓库,SKU) 剩余库存 = 库存表原值 − 「库存消耗」表中该行消耗
- 全量：所有行 剩余 ≥ 0，且 剩余 + 消耗 = 初始库存

### 实施中顺带发现并修复的 2 个引擎 bug（重要）
新增列做全量对账时暴露，非本次需求但影响数据准确性：
1. **替换组主件重复扣减**（库存变负）：Phase 4 输出主件明细时无条件 `pool.qty -= priUsed2`，未区分共享子件。共享主件在 Phase 2 已扣过 pool，此处再扣一次 → `a-us-lx||1633258` 剩余变成 **-7**。
   - 修复：共享主件改从 `allocated` 扣，非共享才从 pool 扣（替代件早先已正确区分）。
   - 结果：负剩余 3 → **0**
2. **共享子件 allocated 未结算**：实例处理完后 allocated 残留未归还 / 超额消耗未补扣，导致 284 行对不上账。
   - 修复：Phase 4 每实例末尾统一结算 `t.allocated`（>0 归还 pool，<0 从 pool 补扣），然后归零。
   - 结果：对账不符 284 → 12 → **0**

### 关键认知（易踩坑）
slot 表的「库存」列 `ch.inv` 是**批次开始时的库存快照**，不是全局初始库存！
同一 SKU 跨「供应商子件 / 单一子件」批次时会递减（如 1838038：供应商批次快照 1420，单一批次 1391，因前者先扣 29）。
→ 对账时必须以**库存表原始值**为基准校验，不能用 `ch.inv`。
