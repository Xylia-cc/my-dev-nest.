## 新增「关系3」：替换组内替代件+主件混用

### 需求（用户确认）
> "同一套bom关系下不能既出现主件又出现该主件的替换件，要再展示关系3，然后覆盖多少套数，使用哪些子件消耗多少个"

经确认，「关系3」的准确含义 = **替换组内混用（替代件 + 主件都消耗）**。

### 先做的调研
检查最新模板（261019）：**不存在**「主件同时作为子件出现」的情况（0 例），排除该种理解。
→ 用 AskUserQuestion 让用户确认，选定"替换组内混用"。

### 判定逻辑与实现（engine.js Phase 4 替换组处理）
替换组组装 k 套，rel1Sets = 各替换组替代件容量最小值：
- 关系1 = rel1Sets 套（纯替代件，altUsed1）
- 关系2/3 = 剩余 (k − rel1Sets) 套：
  - 先用替代件剩余（altUsed2，覆盖 altSets2 套）
  - 不够再由主件补足（priUsed2）

**混用判定**：
```js
var relMixed = (altSets2 > 0 && priUsed2 > 0) ? 3 : 2;
```
- `altSets2 > 0 且 priUsed2 > 0` → 既用替代件又用主件 → **关系3**
- 纯替代件（主件未动）或纯主件（替代件耗尽）→ 仍为关系2

改动点（3 处）：
1. 新增 `relMixed` 变量
2. altUsed2 输出 `relation: relMixed`（原固定 2）
3. priUsed2（主件）输出 `relation: relMixed`（原固定 2）

### 排序
原降序排序 `(b.relation||0) - (a.relation||0)` 天然支持 → 关系3 → 关系2 → 关系1。
已更新注释说明。

### 验证（模板 261019，3000 行消耗明细）
- 关系分布：关系1=2890、关系2=108、**关系3=2**
- 排序：前 2 行为 relation=3 ✓
- 样例（a-eu-hx 父件 1777336，替换组 G:1697642，配比均 1）：
  - 替代件 `1658937`：覆盖 **1** 套，消耗 **1** 个（关系3）
  - 主件 `1697642`：覆盖 **17** 套，消耗 **17** 个（关系3）
  - 合计 18 套 = 该父件组装量 ✓
  - （rel1Sets=0，故无关系1；普通子件 11 个 × 18 套 = 198 套记关系2）

## 修复：关系1/关系2 按批次分行（替代件批次 + 主件批次）

### 用户诉求（附截图）
`a-us-oc 1832933`：需要**分行展示** —— 关系1 = 85套（替代件批次）、关系2 = 73套（主件批次）：
> "不要同一个关系标签下存在替代件 X 消耗 73、主件 Y 消耗 85"

### 根因
1832933 有两个替换组：
- G:1658950：替代件 `1733137` 库存 **85**（可组85套）、主件 `1658950`
- G:1838038：替代件 `1739104` 库存 **0**、主件 `1838038`

`rel1Sets` 取各替换组替代件容量最小值 → `min(85, 0) = 0`
→ 关系1 = 0，全部挤进关系2/关系3，且替代件(85套)与主件(73套)被混在同一个「关系3」标签下。

### 修复（engine.js）
1. **rel1Sets 忽略替代件库存为 0 的替换组**：判定条件加 `capSets > 0`，避免被 0 拉低。
2. **关系1 批次增加主件补足**：新增 `priUsed1 = (sets1 - altSets1) * priRatio`，替代件不足（含为0）时由主件补足并输出 `relation=1`。
3. 新增 `consumePrimary(qty)` 统一处理主件扣减（共享→allocated，非共享→pool），关系1/关系2 共用。

### 修复后（与截图完全一致）
`1832933 a-us-oc` 组装 158 = 85 + 73：
- **关系1**：16 行 × 85 套（含替代件 1733137、主件 1838038；**不出现 1658950 主件**）
- **关系2**：16 行 × 73 套（含主件 1658950、主件 1838038；**不出现 1733137**）
- 关系3：本案例不再触发（混用已拆到关系1/关系2）

### 校验（3 个模板）
明细行 3859 / 3011 / 521，**负剩余 0、超库存 0、脏行 0**；关系分布仅关系1/关系2。
关系3 仍保留，仅在「关系2 批次内替代件+主件混用」时触发。

## 重构（终版）：三批次按关系标签分行 —— 关系1 / 关系3 / 关系2

### 用户诉求
"父件消耗明细最终结果要分出每个关系标签，不能存在同一个关系标签下替代件混用的情况"
并提供了期望样例 `呈现结果.xlsx`。

### 期望样例揭示的正确结构（关键）
样例中 `1832933` 分为三批，每批都是完整 BOM 展开：
- **关系1 = 30 套**：纯替代件批次（1733137 + 1739104 两个替代件都在）
- **关系3 = 55 套**：混用批次（1733137 替代件 + 1838038 主件）
- **关系2 = 50 套**：纯主件批次（1658950 + 1838038）

→ 证明**上一版"rel1Sets 忽略替代件为0的组"是错的**，会吞掉关系1、并把混用塞进关系1。

### 正确的三批次定义
```
rel1Sets  = min(各替换组替代件容量)   // 纯替代件批次套数（含 0：某组替代件为 0 时关系1 即为 0）
altMaxSets= max(各替换组替代件容量)   // 混用批次结束点
sets1 = rel1Sets               → 关系1（所有组都用替代件）
sets3 = altMaxSets - rel1Sets  → 关系3（部分组继续用替代件、部分转主件）
sets2 = k - altMaxSets         → 关系2（所有组替代件耗尽，全用主件）
```
普通子件同样按 1→3→2 顺序切分输出三行。

### 修复的 2 个 bug
1. **替换组块内残留旧定义**：`var sets2 = k - rel1Sets`（第773-774行）覆盖了新的三批次变量 → 关系2 算出 105 套、普通子件消失。已删除。
2. **rel1Sets/altMaxSets 按单个替代件取 min/max**（多替代件场景错）：改为**按替换组聚合容量**（`groupCap = Σ floor(avail/ratio)`）后再取 min/max。否则多替代件测试期望覆盖20实得23。

### 结果（1832933 a-us-oc）
组装 135 = **30 + 55 + 50**（需求158，瓶颈 1733137 可组135套）：
| 关系 | 行数 | 覆盖 | 构成 |
|---|---|---|---|
| 关系1 | 16 | 30 | 替代件 1733137、1739104 + 14 主件 |
| 关系3 | 16 | 55 | 替代件 1733137 + 15 主件（含 1838038） |
| 关系2 | 16 | 50 | 全主件（1658950 + 1838038） |

**顺带修正超扣**：上一版 1658950 消耗 73 但库存仅 50（超扣 23）；本版消耗 50 ✅
