## 修复：替换组共享子件 Phase 3 瓶颈计算 bug

### 问题现象
用户反馈：`a-us-mq 1806067` 组装量为 0，但各子件库存充足。

### 根因分析
通过调试日志追踪发现：
1. `1806067` 的 `k_theory = 926`，所有 slot 容量均 ≥ 926
2. 但 `k_actual = 0`，被替换组主件 `1826968` 的 `allocated=0` 拉低
3. `1826968` 在 a-us-mq 库存仅 14，被同仓更高销量父件 `1806065`（销量 45.51）全部拿走
4. 然而 `1806067` 的替代件 `1797082` 库存充足（14897），根本不需要动用主件 `1826968`
5. **bug 所在**：Phase 3 计算 `k_actual` 时，对替换组内每个 child 独立检查 `allocated`，没有合并计算替代件+主件的总 allocated

### 修复内容
修改 `engine.js` 两处：
- **Phase 3**（line 528-542）：替换组（slot.children.length > 1）合并所有 children 的 allocated 计算 maxSets
- **Phase 3.5 步骤 3**（line 621-634）：重新计算 k_actual 时同样合并替换组 allocated

### 修复后结果
- `1806067 a-us-mq`：组装量 0 → **926**（齐套满足）
- `1806065 a-us-mq`：组装量保持 **192**（不受影响）

## 修复：rel1Sets 计算逻辑 bug（消耗明细缺失子件）

### 问题现象
用户反馈：`a-eu-fy 1728820` 父件消耗明细中缺少子件 `1752611`。

### 根因分析
1728820 有两个替换组：
- G:1752611：替代件 1729153 库存=0，主件 1752611 库存=4864
- G:1734993：替代件 1729155 库存=217，主件 1734993 库存=3574

`rel1Sets` 计算逻辑（line 669-691）：
```js
var rel1Sets = 0;
if (rel1Sets === 0 || capSets < rel1Sets) rel1Sets = capSets;
```
- 处理 G:1752611 时：capSets=0，rel1Sets=0，条件成立 → rel1Sets=0
- 处理 G:1734993 时：capSets=108，rel1Sets=0，`rel1Sets === 0` 仍为 true → rel1Sets 被覆盖为 108

**bug 所在**：初始值 0 和 `rel1Sets === 0` 条件导致后续更大的 capSets 覆盖了前面更小的 capSets。rel1Sets 本应为 0（min(0, 108)），却被错误算成 108。

后果：sets2 = k - rel1Sets = 0，主件补足逻辑 priNeed2 = 0，主件 1752611 完全不输出到消耗明细。

### 修复内容
- rel1Sets 初始值从 `0` 改为 `-1`（哨兵值，表示未设置）
- 比较条件从 `rel1Sets === 0 || capSets < rel1Sets` 改为 `rel1Sets < 0 || capSets < rel1Sets`

### 修复后结果
- `1728820 a-eu-fy`：消耗明细从 10 个子件 → **11 个子件**（补回 1752611）
- 关系分配：rel1Sets=0，sets2=108，所有子件统一标记为关系2（符合定义：替代件最缺的替换组决定关系1套数）
